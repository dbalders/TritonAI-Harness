# Mobile development lifecycle

## UCSD iOS signing

The iOS app uses the University of California, San Diego (Business Affairs)
team (`G789749RTK`). Production uses `edu.ucsd.tritonai.harness`; development
and preview append `.dev` and `.preview`. Widget and sharing extension IDs,
and the matching App Group, derive from the selected iOS bundle identifier.
Expo prebuild reads these values from `apps/mobile/app.config.ts`; changing
only the generated Xcode project will not persist across a clean prebuild.

The production EAS submit profile targets UCSD's TritonAI Harness App Store
Connect record (`6813147394`). Signing certificates and provisioning profiles
must belong to UCSD.

EAS Build and Update use the existing `@dbalders/t3-code` Expo project
(`dec81a5b-db3d-4de0-a00c-532e6e456a98`). The app's `owner`,
`extra.eas.projectId`, and `updates.url` must stay aligned with that project;
the `t3-code` slug is retained to match its existing Expo identity. Regenerate
native projects after changing this configuration. Installed binaries need a
new native build to adopt the new update URL.

The repository still contains upstream Clerk associated domains. Configure
TritonAI authentication and verify EAS credentials and environment variables
before publishing builds or OTA updates. Project linkage and signing settings
alone do not establish release readiness.

## Preview on TestFlight and Xcode

TritonAI Harness Preview has a separate UCSD App Store Connect record
(`6813180967`) and bundle ID (`edu.ucsd.tritonai.harness.preview`). It can be
installed alongside production. Both variants read their version from
`app.config.ts`; their build numbers and TestFlight groups are independent.

Use the `preview:testflight` EAS build and submit profile for store-signed
Preview builds. It selects `APP_VARIANT=preview`, the preview environment and
update channel, and submits to the Preview app record. The existing `preview`
and `preview:dev` profiles retain internal/ad hoc distribution for development.
Do not use the production submit profile for a Preview build.

Local Xcode builds also set `expo-channel-name` from `APP_VARIANT`, so Preview
and production request updates from their respective channels. The iOS
`buildNumber` in app config applies to local Xcode builds; EAS production and
TestFlight profiles use remote build-number management and auto-increment.

For a local Xcode build, run these commands from `apps/mobile` in a dedicated
checkout with dependencies installed:

```sh
APP_VARIANT=preview npx expo prebuild --platform ios
open ios/TritonAIHarnessPreview.xcworkspace
```

Prebuild generates the native name, artwork, bundle IDs, entitlements and App
Group for Preview. In Xcode, select the UCSD team (`G789749RTK`) and automatic
signing for the main app, widget and sharing targets. The Preview App Group is
`group.edu.ucsd.tritonai.harness.preview`; production uses its own group.
Select the Preview scheme and Any iOS Device, then Product > Archive. In
Organizer, use Distribute App > App Store Connect to upload to Preview's
TestFlight record. A successful upload still needs Apple processing before
it can be installed by testers.

Changing an Xcode Run-scheme environment variable alone does not switch an
already generated production project to Preview. Generate the desired variant
before opening Xcode. Keep separate checkouts for simultaneous production and
Preview workspaces; native `ios/` files are generated and gitignored. Local
archives do not establish compatibility with fingerprints generated by Linux
EAS workflows, so verify that separately before publishing OTA updates.

## Development refresh

The [connection runtime's HMR boundary](../../apps/mobile/src/lib/hot-swappable-atom-runtime.ts)
keeps a stable atom runtime and replaces its Effect layer through a writable atom.
It accepts the update only after installing the new layer. Otherwise importers
retain the old behavior even though Metro reports a successful refresh.

Do not reset the shared atom registry to refresh a connection-runtime edit. Reset
removes listeners from mounted consumers that Metro has no reason to rerender.
When the registry or managed-runtime module itself changes, normal Metro propagation
disposes its old resources. This boundary does not make arbitrary module-level atom
families safe to hot-swap. Production uses an ordinary atom runtime.

[Environment supervisor scopes](../../packages/client-runtime/src/connection/registry.ts)
are children of the registry scope. The per-environment map supports targeted
shutdown, but a supervisor created after its cleanup runs would escape it. A closed
parent scope also closes late arrivals, preventing interrupted startup or runtime
replacement from leaving a WebSocket alive outside the new registry.

The [Uniwind patch](../../patches/uniwind@1.11.0.patch) still compiles CSS on Metro
updates so newly used classes are discovered. It skips global style invalidation
only when the generated stylesheet and theme list are unchanged. Skipping compilation
would lose new classes; invalidating every consumer for unchanged output makes an
ordinary component edit refresh the whole app. The fingerprint is recorded only
after initialization succeeds.

The native modules under `apps/mobile/modules/` are `file:` dependencies, and pnpm
copies those into its virtual store instead of linking them. Metro bundles the copy,
so an edit to a module's TypeScript is invisible to a running dev client until
`vp i` re-syncs it, while Gradle and CocoaPods compile the worktree directory
directly. A JavaScript change that "has no effect" on device is usually this.
